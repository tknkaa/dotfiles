description: PR の差分をユーザーと一緒に読んで理解し、その後に選択式クイズで理解度を測る。PR 番号を渡されたとき、または「PR を一緒に読みたい」「PR の理解度を確認したい」「PR クイズ」と言われたときに使う。
---

PR の差分をユーザーと一緒に読み、理解を深めたうえで、選択式クイズで理解度を測る。進め方は「読む → クイズ」の 2 フェーズ。

## 準備

引数は PR 番号。なければユーザーに聞く。`gh pr view <番号>` で目的・説明を、`gh pr diff <番号>` で差分を読む。必要なら関連ファイルの周辺コードも読む。差分を読む前に、解説もクイズも始めない。

## フェーズ1: 一緒に読む

1. **全体像を伝える。** PR の目的、変更ファイルの一覧、変更の流れを数文で説明する。差分の大きさに応じて、いくつの塊に分けて読むかを示す。
2. **塊ごとに読み進める。** 関連する変更(ファイル単位、または機能単位)を 1 塊として、次の順で説明する。
   - その塊が何をしているか。変更前後の挙動の違い。
   - なぜそうしたのか。根拠が PR 本文やコードから読み取れるときだけ述べる。読み取れないことは推測で補わず、「ここは読み取れない」と言う。
   - 見落としやすい前提、副作用、壊れうる箇所。
   - 参照は `file:line` で示す。長い差分を丸ごと貼らない。
3. **塊の終わりで止まる。** 「質問がなければ `can` と入力すると次へ進む」と案内する(初回で伝えればよい)。質問や、分からない点があれば、答えてから次へ進む。ユーザーが質問したら、差分とコードに基づいて答える。質問が続く間は、次の塊に進まない。
4. **先を急がない。** ユーザーが `can`(または「次へ」「分かった」)と言うまで進めない。`can` は、質問なしで次へ進む合図として扱う。全部の塊を読み終えたら、読んだ内容を短くまとめ、クイズに進んでよいか確認する。ユーザーが先にクイズだけを望むなら、フェーズ1を省く。

## フェーズ2: クイズ

1. **問題を作る。** フェーズ1で扱った内容から、差分の大きさに応じて数を決める。小さい差分は 3〜5 問、大きい差分は多めにする。
   - なぜその変更が必要か、変更前後の挙動の違い、壊れうる箇所、副作用を中心に出す。
   - 特に、フェーズ1でユーザーが質問した箇所や、つまずいた箇所は、理解の確認として出す。
2. **一問ずつ出す。** AskUserQuestion で選択式にし、回答を受け取ってから次の問題を出す。まとめて出さない。
   - 選択肢は 3〜4 個。正解が一つに定まり、誤答は「ありそうな誤解」にする。
   - 正解の位置は偏らせない。ラベルで正解が分からないようにする。
   - 答えの根拠は、差分、PR 本文、コードから読み取れるものだけにする。
3. **回答ごとにフィードバックする。** 正誤を示し、根拠になる `file:line` を添えて 1〜3 文で解説する。不正解のときは、その選択肢がなぜ誤りかも述べる。
4. **最後に総括する。** 正答数、理解できていた点、弱かった点を短くまとめる。弱かった点は、読み直すと良い箇所を挙げる。

## 守ること

- 一緒に読むのは理解のため。説明は、ユーザーが追える量に絞る。
- クイズの答えを、出題前に漏らさない。フェーズ1の説明は、クイズの答えを直接言う形にならないよう気をつける。ただし、理解に必要な説明は削らない。
- 評価はユーザーの理解についてのみ行う。PR の良し悪しのレビューはしない。
